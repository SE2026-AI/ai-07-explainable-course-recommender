# Reliability and failure handling feature
Read common-context.md, accepted quality targets and integrated service boundaries. Define and implement proportionate failure behavior.
Allowed writes: assigned orchestration/error handling under src/backend/, API adapter error handling under src/web/ only if web owner delegates exact files, test/integration/test_failure*, docs/architecture/RELIABILITY.md.
Specify source, stimulus, environment, response and measurable response for each adopted reliability scenario. Ranking failure may offer a clearly labeled catalog fallback only when eligibility can still be validated. Explanation failure must not invent reasons; use supported structured/template evidence. Catalog failure must stop fresh recommendations and preserve the user's existing plan where implemented.
Distinguish degraded from normal, unavailable, empty and stale responses. Add bounded timeouts/retry only for actual external boundaries. Keep retries safe. Do not adopt RE-094 load/retention parameters or promise availability without agreement and evidence.
Acceptance: injected failures produce documented status, correct safe fallback and bounded response; unavailable catalog cannot yield fabricated recommendations; unaffected plan state survives according to contract. Record exact environment and measured results or mark performance checks unrun. Handoff reproducible failure-demo steps.
